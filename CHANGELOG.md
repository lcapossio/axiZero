# Changelog

All notable changes to axiZero will be documented in this file.

## [Unreleased]

### Fixed

- **`MixedIdWidthSpec`** — 2 tests, the first root tests that build a configuration whose masters declare different numbers of IDs. `Axi4IdWidener` sits on the master-side path in `AxiZeroTop` whenever a port is narrower than the fabric, and no root test had ever configured one: its only exercise was through the VexRiscv example, a separate sbt project, so a checkout that never built that example had nothing covering it — the coverage report showed the file at 0%. Both tests check the ID a response came back under rather than only the data, because the padding is constant zero outward and the truncation back is exact only if the fabric returns those same zeros. Mutation-verified: shifting the ID by one bit makes a response arrive under the wrong ID and the suite fails.

- **Coverage is now a gate rather than an artifact.** CI ran `coverageTest` and uploaded the HTML report, but nothing failed when coverage fell -- the number was only ever seen by someone who went looking, which is after the fact. `build.sbt` sets floors of 78% statement and 55% branch with `coverageFailOnMinimum`, a few points under the measured 82.30% and 58.40%, so a refactor adding a defensive branch passes and a lost suite does not. Verified by raising the floor and watching the build fail.

  `axizero.gen` is excluded from the measurement. It holds the `main` entry points that write the tracked netlists, `sbt test` never runs a main, and so 866 statements scored 0% while being gated harder than anything that was counted — CI runs each one and `check_generated.py` compares all 15 netlists byte for byte. Counting them made the report say a quarter of the code was untested when what it meant was that some of it is tested by something else; statement coverage reads 82.30% rather than 74.45% once they are out. Branch coverage stays much lower than statement because a branch here is usually a configuration choice and no test builds every combination — a real gap, and the floor is set to stop it widening rather than to bless it.

- **`Axi4LiteWidthConverter` put write data on the wrong byte lanes.** A narrow AXI4-Lite master on a wider fabric had its WDATA and WSTRB zero-extended into the *low* lanes and its RDATA taken from the low lanes, whatever the address said. AXI places a transfer on the lanes its address selects: a 16-bit master writing at `0x2` on a 32-bit bus must drive lanes 2..3 with WSTRB `0b1100`, and it drove lanes 0..1 with `0b0011` instead. A slave that decodes the address read the upper half and found nothing there, and a second write to the other half of the same word destroyed the first. The converter now shifts data and strobe onto the lanes the address chooses, and takes read data back off those same lanes. Because W carries no address and AXI4-Lite allows W before AW and several writes in flight, the lane offset is captured from AW (and AR) into a small queue and applied to the beat it belongs to; `outstanding` sets its depth.

  The defect was invisible to every existing test: with a 16→32 converter the lane-select bit is address bit 1, and the suite's addresses were `0x0`, `0x4` and `0x8` — all of them zero in that bit, so the data always happened to belong exactly where the zero-extension put it. Two tests now cover it, both mutation-verified against the old RTL.

- **The AXI4-Lite and full AXI4 simulation slaves ignored WSTRB**, storing each write beat whole. No test asserting that untouched bytes survive a partial-strobe write could ever have failed, which is why the coverage report has carried that as a gap. Both models now merge by strobe, on the same helper the IPIF model already used, and the Lite model keys its memory on the bus word rather than the raw address — a half-word write at `0x2` belongs in word `0x0`, and keying it separately meant the lane it travelled on was never checked.

- **A narrower AXI4-Lite slave than the fabric now fails with a reason.** `AxiZeroLiteTop` wired the width converter backwards for that case — the component is built around a narrow *master* — and elaboration died in 39 autoconnect direction errors naming signals rather than the cause. The configuration is rejected up front with a message saying what is unsupported. Narrowing at a Lite slave port remains unimplemented.

### Added

- **`RegSliceSkidSpec`** — 6 tests, the first that tell `regSliceSkid` apart from the plain register slice. It is on the AW/W/AR path of every registered master on both boards, and until now the only evidence it did anything was that timing closed. The tests measure what it buys: a stalled plain slice accepts one beat and a skid two; the plain slice's READY is combinational from the far side and the skid's is not, shown by stalling and releasing on the same cycle; 400 beats survive random back-pressure through both with their payloads intact and in order; latency stays one cycle and throughput full either way; B and R keep the plain slice they are given rather than quietly getting a skid; and the Lite slice behaves the same. Mutation-verified — disabling the skid fails three of them.
- **A write-response identity check in `MultiIdOrderingSpec`** — a second test, and an error-returning slave in the first. B carries nothing but an ID and a response, so a BID exchanged between two *busy* IDs is invisible when every slave answers OKAY, which is what the existing scoreboard was watching. One slave now returns SLVERR, which gives each write response an identity tied to where it was sent, and the run asserts it saw both kinds. The new test feeds that scoreboard three traces directly: an exchanged BID, caught; a same-ID response reordering, caught; and a correct trace, clean.

- **A write-only error region, and a per-ID expectation queue for write responses** (`errRegionBase` on `AxiMultiIdGenConfig`). A BID exchanged between two IDs that are both waiting is the one failure the read-back cannot reach: W beats follow the AW that preceded them, so a mislabelled B moves no data and memory ends up correct either way. The error is in the label, and a label is an ID and two bits of status — between two targets that both answer OKAY the swapped trace and the correct one are the same bits, which is AXI4 and not this fabric. Each generator now writes one extra single-beat burst per round to an address **no slave claims**, which the crossbar's own `Axi4DecErrSlave` answers with DECERR, and each ID keeps a queue of what its outstanding writes are owed. `errRespSeen` reports that an error really came back and `io.genOk` requires it, so a bitstream that never exercised the check cannot pass it. Closes on silicon what `MultiIdOrderingSpec` closed in simulation, and puts the decode-error responder on a board for the first time — until now it was only ever exercised in simulation. Costs the Arty build 203 LUTs and 0.22 ns of slack; a slave added for the purpose, which is where this started, cost 942 LUTs and left only +0.017 ns.

### Changed

- **Each multi-ID generator's port is now sized to its own ID count** rather than to the widest generator's, and the second `stress_ids` generator runs two IDs instead of four. `Axi4IdWidener` sits in every mixed-width design here, but with every generator built to the same width the only narrow master on either board was the CPU, whose ID is a constant — so the zero-extension was carried by a signal that never moved, which is where a padding or truncation bug survives a bitstream. The two-ID generator now reaches the fabric one ID bit wide against the fabric's two, with an ID that varies, and two IDs still leaves the ordering rule something to hold: one ID crossing while the other is live.
- **Both board runners now watch the verdict instead of reading it once.** Each sampled the design a fraction of a second after configuration and called that the result. Every verdict either board reports is sticky — a generator error, a protocol violation and a checker that lost track all latch and never clear — so a fault appearing a second later is real, is still being reported, and was simply never looked at; and the first read is the least traffic the generators will ever have run behind them. The Arty runner now compares every later UART report line against the first for `--observe` seconds (default 5), and the DE25-Nano runner re-reads the verdict word over JTAG-AXI the same way. A verdict that moves fails the run, with both values printed.

### Removed

- **`generated/fcapz_axi_interconnect.v`** — an untracked netlist with no producer in this repository and no consumer, left over from an unrelated design.

## [0.4.0] — 2026-09-16

### Added

- **`AxiSatGen` — a synthesizable saturating self-checking AXI4 master** (`hw/spinal/axizero/verif/`). The SpinalHDL successor to `hw/vivado/arty_a7/ip/rtl/axi_sat_gen.v`, which could only ever be dropped into a Vivado block design beside a MicroBlaze. It plugs into an axiZero port directly, simulates in SpinalSim with the rest of the design, and generates for Vivado and Quartus from one source. It keeps several bursts in flight so AW runs ahead of W and of B — a master that waits for each response never makes an arbiter choose — and it reads back every word it wrote, which is possible without storing anything because the data is a function of the address (`data(k, p) = dataPattern | (p << 16) | k`). Burst length varies per pass, `1 << (p % 4)` beats, so both regimes an arbitration policy behaves differently in are covered. Write data is deliberately not gated on AWREADY: AXI4 A3.3.1 permits data before address, and a slave that merges the two into one shared command channel — SpinalHDL's `Axi4Shared`, for one — will not accept AW until a W beat is there to go with it, so a generator that waited would deadlock against it and never issue a burst.
- **`AxiSatGenSpec`** — 4 tests. A full run against a working RAM reports no errors and laps; the generator's own traffic is put through `Axi4ProtocolChecker` and found protocol-legal, so it cannot quietly poison a stress run; a RAM rigged to drop a byte lane is caught, which is the one test that says the checking is real rather than merely present; and `enable` low keeps it off the bus entirely.
- **`trafficGens` in `VexZeroSocConfig`** — attaches any number of `AxiSatGen` masters to the example SoC after the CPU, host and video ports, each owning a window of RAM. Overlapping windows, or one that lands on the firmware's region, are rejected at elaboration rather than reported later as a data error that looks like a lost beat. Their verdict comes out on `io.genOk` / `io.genFault` as wires and folds into `VexZeroChecks`, so no firmware MMIO polling is involved — which is what the retired MicroBlaze suites needed, and where one of them had a hardware failure caused by generators writing status words into aliased BRAM.
- **`axi3DataPath` in `VexZeroSocConfig`** — routes the CPU's load/store port through AXI3 and back through `Axi3ToAxi4Adapter`, so every load, store and cache refill the program makes crosses the adapter. That is a harder test of it than a traffic generator is: the CPU stalls on the answer, so a lost or mis-ordered response hangs the boot rather than being counted.
- **`Axi4ToAxi3`** — the AXI4-to-AXI3 wire shim as a reusable helper, replacing the hand-written copy inside `ArtyAxi3DutGen`. Every optional AXI4 field is optional here too, because the buses it is used on are real ones: VexRiscv's data bus carries no LEN, no BURST and no LOCK at all, and an absent field is driven to what a single-beat INCR transfer would carry.
- **`axisSmoke` in `VexZeroSocConfig`** — brings `AxiStreamArtySmoke` into the SoC as an island beside the bus, verdict on `io.axisOk`. It shares nothing with the crossbar but the clock, so it costs a bitstream almost nothing to carry — which is why the four stress builds all carry it and there is no AXI4-Stream build of its own.
- **`VexZeroStress`** — the four loaded configurations in one object: round robin, weighted round robin 3:1, QoS across three ranks (CPU 12, gen0 6, gen1 2), and round robin with the AXI3 data path. The simulation and both board generators build from it, because a hardware run confirms a simulation only if the two were the same design.
- **`VexZeroGenStressSpec`** — 4 tests, one per board build, each asking three separate questions of a fabric that is contended **97–98% of the time**: does it still move the right data (every generator's read-back plus the firmware's own checksum, LEDs and characters); does it still obey AXI4 (a protocol checker on every port); and does the policy do what it claims. The third is what the retired suites existed for and what no value check can reach. Round robin splits two identical generators 1.00:1; weighting them 3:1 moves it to 1.78:1 with neither starved; QoS 6 against 2 gives 1.51:1 while the CPU ranked at 12 keeps a shorter worst-case fetch than either. A 3:1 weight does not buy 3:1 throughput and is not meant to — the generators are closed-loop, so a weight buys a share of the grants. Contention is asserted rather than assumed, because a test that ran under no load would pass while proving nothing.
- **Four loaded hardware builds, for both vendors** — `stress_rr`, `stress_wrr`, `stress_qos` and `stress_axi3`, generated by `VexZeroStressArtyGen` / `VexZeroStressDe25Gen`, built by `create_project_vexzero.tcl` and `build_vexzero_de25.tcl`, and run by `run_vexzero_test.py --design all` and `run_vexzero_de25.py --design all`. Together with `verdict` they replace the six retired MicroBlaze suites, and unlike those they run on Altera as well as Xilinx.
- **`AxiMultiIdGen` — a synthesizable self-checking AXI4 master that varies its transaction ID** (`hw/spinal/axizero/verif/`). AXI4 orders transactions that share an ID and a direction, whichever slave each one went to, and the crossbar keeps that promise with the industry's single-slave-per-ID rule. That machinery is the one part of the design whose correctness depends on a master actually using more than one ID — and nothing in this repository did: VexRiscv drives a constant ID and so does `AxiSatGen`, so every bitstream ever built here exercised the ordering table in its degenerate shape. This generator runs several IDs at once over two windows in two different slaves, and issues one ID's *consecutive* bursts to *different* slaves, which is the single-slave-per-ID rule's own case: the fabric may not admit the second until the first has retired. It checks the ordering promise directly in hardware, with no scoreboard in Scala — each ID owns a queue of the bursts issued under it and every R beat is compared against the head of the queue its RID names, so a same-ID response that overtook an earlier one, a response returned under the wrong RID and a burst answered with the wrong number of beats all land as errors. Data is a function of the address as in `AxiSatGen`, with the region in it, so a burst answered out of the wrong slave reads back as a wrong value rather than a plausible one. It also reports whether more than one ID really was outstanding at once and whether an ID really did ask to move between slaves while live, because a clean run without both proves nothing.
- **`AxiMultiIdGenSpec`** — 5 tests. A clean run against a two-RAM crossbar, with both pieces of evidence asserted; a RAM rigged to drop a byte lane, caught; **two same-ID reads answered out of order by a deliberately reordering RAM model, caught**; the same control in order, clean; and a stalled fabric detected. The third is the one that matters: a self-checking generator that cannot fail is worth nothing on a board, so the ordering check is shown failing before it is trusted.
- **`Axi4OrderingProbe` — the single-slave-per-ID rule watched where it is actually enforced** (`hw/spinal/axizero/verif/`). `AxiMultiIdGen` checks the fabric's ordering *promise* from its own boundary: it issues traffic and compares what comes back. What it cannot see from there is the rule the fabric keeps that promise with, because a register slice sits between the two — the skid accepts requests the crossbar has not admitted, so a generator can truthfully report "several IDs in flight" and "a live ID asked to cross" while the crossbar downstream was serializing everything and its ID table never held two IDs at once. The evidence would be true and would prove nothing about the machinery it is named after. This probe watches the crossbar's *own* master port, where ARREADY is the admission decision itself, and does two jobs: it **latches a violation** when the fabric admits a request for one region while that ID still has work outstanding in the other — seen directly, rather than inferred from a response arriving in the wrong order, which matters because two similar slaves can answer in issue order by luck — and it **latches the evidence** that the interesting case was reached, `deepCrossHeld`: a crossing request presented and *not* admitted while two or more of that ID's bursts were live at the other region. Reads and writes are tracked apart, because AXI4 orders each direction on its own. Passive like `Axi4ProtocolChecker`, and built as an `Area` with no ports, so wiring it in cannot change what the design does. Its verdict gates `io.genOk`, so a `stress_ids` bitstream that never reached the case now **fails** rather than passing quietly.
- **`pipelineInputs` on `Axi4OrderingProbeConfig`** (default on) — registers everything the probe observes, so its per-ID comparators sit behind a register instead of hanging off the live bus. Without it the arbiter's ARREADY reached a chain of per-ID compares in the cycle it was decided and `stress_ids` did not close at 100 MHz on the Arty: WNS **−0.389 ns**, measured. With it the build closes at **+0.342 ns** and the probe costs the fabric no path at all. The verdicts are identical because every signal the probe sees is delayed by the *same* cycle, which is not left as an argument in a comment: `Axi4OrderingProbeSpec` runs every one of its sequences against both settings and requires both to agree. Same reasoning and the same switch as `pipelineInputs` on `Axi4ProtocolCheckerConfig`.
- **`Axi4OrderingProbeSpec`** — 6 tests, all of them about the probe being able to fail. The rule broken with **every response still in issue order**, caught (a probe that waited for a wrong answer would call that run clean); a request admitted on the very cycle the last outstanding one retires, correctly *not* called a violation; a crossing request held against two live bursts setting `deepCrossHeld`; one-burst-at-a-time traffic claiming no evidence it did not earn; two IDs live recorded, and an ID live at one region for reads and the other for writes correctly left alone; and the same violation on the write channels, caught. A probe that latches nothing reads exactly like a fabric that behaved, so it is shown failing before its verdict is trusted.
- **`observeMasters` on `AxiZeroConfig`** (`Axi4MasterObs`) — brings the crossbar's own master ports out of the fabric as a read-only observation bundle, one per master. They are two components deep, so nothing outside could read them, and they are the only place where READY means *admitted* rather than *taken into a register slice*. Requests and responses only — who asked, where, and whether it was taken — and the signals are copies of wires that already exist, so anything not read is pruned before synthesis. Off by default, and rejected on an all-Lite fabric, which carries no IDs to observe.
- **`ram2Base` and `multiIdGens` in `VexZeroSocConfig`** — a second on-chip RAM as a second full AXI4 slave, and any number of `AxiMultiIdGen` masters driving IDs between the two. One slave is enough to load a fabric but not to test how it orders: the same-ID rule is about transactions that go to *different* slaves, so with one full slave it is never asked for anything. Both default off, the second RAM is appended after every existing slave and the generators after every existing master, so every other design decodes and generates exactly as before. Windows are validated at elaboration against the firmware, each other and the saturating generators' windows.
- **`stress_ids` — a fifth loaded hardware build, for both vendors.** Round robin, a second 4 KiB RAM at `0x9000_0000`, and two multi-ID generators running four IDs each with up to four read bursts in flight per ID, sent to the two RAMs in pairs. Everything the other four carry — the firmware self test, a protocol checker on every fabric port, the AXI4-Stream island — it carries too, so what it adds is the ordering traffic and not a different design. It is the first bitstream in this repository whose masters do not all drive a constant ID. Verified on both boards: the Arty reports `VZPDRCLBGSF` at 9646 LUTs, 8319 registers, 11 block RAM tiles, WNS +0.342 ns at 100 MHz (103.5 MHz Fmax, Vivado 2025.2 on `xc7a100tcsg324-1`); the DE25-Nano reads back verdict word `0x00000706` at 13,413.4 ALMs (28%), 19,574 registers, 297,232 bits of block memory, worst setup slack +9.404 ns at 50 MHz (Quartus Prime Pro 26.1 on `A5EB013BB23BE4SR1`). Those figures include the ordering probes. It is the largest build on both boards, and the size is the system rather than the crossbar: six masters and five slaves instead of four and three, plus four per-ID expectation queues in each generator and two more protocol checkers. In simulation, over the same 60,000-cycle window the other four are measured on and at 100.0% contention, the two generators each lapped 10 times with zero data, response and ordering errors, both reporting several IDs outstanding at once and a live ID asking to cross to the other RAM — and both ordering probes, watching the crossbar's own master ports, recorded two IDs live, one ID two bursts deep, and a crossing request held against two live bursts, with no violation.
- **Mixed master ID widths in `AxiZeroMixedTop`** (`Axi4IdWidener`) — master ports need no longer agree on their ID width. The fabric carries the widest of them and a narrower port's IDs are zero-extended on the way in and truncated on the way back, which is exact because the padding bits are constant zero on the request path. Stateless, and inserted only where the widths differ, so a design whose masters all declare the same width generates byte-identical Verilog to before. Without it a CPU with one ID could not sit on the same crossbar as a master that runs four, which is what `stress_ids` needs.
- **`scripts/test_axizero.py`** — unit tests for the YAML front end's Scala emitters and config validator, run in CI before the end-to-end generate. They import `axizero.py` directly and need neither sbt nor a JDK, so a mistake in a port template is caught in milliseconds instead of at the far end of an elaboration.
- **`regSliceSkid` on `MasterPort` and `SlavePort`** — makes a register slice a full pipe (`s2mPipe` + `m2sPipe`) on the three forward channels, so the READY it presents upstream is a register rather than a wire running back through the fabric. `Stream.stage()` alone is `m2sPipe`: it registers VALID and the payload and leaves `upstream.ready = !rValid || downstream.ready` combinational, which is correct and loses nothing, but means an arbiter's grant can reach a master's READY in the same cycle. The skid register is what makes registering READY safe — once READY is a cycle stale the upstream can complete a handshake the downstream did not accept, and the extra storage catches that beat. Forward latency and throughput are unchanged, because the skid only fills on a cycle the upstream would have been stalled anyway. Only AW/W/AR get it: B and R carry READY from the master back into the fabric, which on the measured builds is not where the long paths are. Needs `regSlice`, and off by default, so every existing configuration generates exactly as before. Reachable from the YAML front end as `reg_slice_skid` on a master or slave port, validated there against `reg_slice` the same way the Scala `require` does.
- **`pipelineInputs` on `Axi4ProtocolCheckerConfig`** (default on) — registers everything the checker observes, so 19 rules' worth of comparison logic sits behind a register instead of hanging off the live bus. The checker is passive and its only output is a set of sticky bits read at the end of a run, so delaying every signal it sees by the same cycle leaves every rule's verdict identical — but it takes the checker off the fabric's critical path entirely. On the loaded Arty builds this alone moved `stress_qos` from WNS −1.902 ns to −1.021 ns, and the count of failing endpoints from 821 to 255.
- **`slaveRegSlices` and `masterRegSliceSkid` in `VexZeroSocConfig`** — register slices on the slave ports, and full pipes on the master ports, both on for the four stress builds and off elsewhere. With the checker pipelining above they are what close timing on the loaded designs: `stress_qos` went −1.021 → −0.552 ns with the slave slices and −0.552 → **+0.316 ns** with the master skid, 68 failing endpoints to none. The arbitration shares are bit-identical across all three steps, which is the point — the fix is structural and changes no decision the arbiter makes.
- **A hardware verdict register at `sysCtrl + 0x10`** — the bus-protocol, traffic-generator and stream-island verdicts as a word a host can read over the bus, each with a matching "present" bit so a build without checkers cannot be mistaken for one that passed. The Arty prints these on its serial line; a board whose only link to a host is a debug cable has none, so the DE25-Nano runner reads them across the crossbar under test — a fabric broken badly enough to hide its own verdict cannot report a pass either.

- **`idThreads` on `AxiZeroConfig`** (default 2, `id_threads` in YAML) — the size of the pipelined crossbar's table of live transaction IDs, per master per direction. It is what enforces AXI4's same-ID ordering rule; see the two entries under Fixed below for what it enforces and why. Small and fixed the way AMD's, Arm's and Forencich's are rather than one entry per ID value — a request whose ID matches no live thread waits for a free one, which costs throughput under many-ID traffic and never correctness. `idThreads = 1` gives a master one destination in flight per direction, which is already what a constant-ID master gets, so every design in this repository behaves identically at either setting.

### Changed

- **`AxiMultiIdGen` issues a *pair* of bursts at one region before crossing.** It used to alternate region on every burst, so an ID crossed while exactly one of its bursts was live — the shallowest form of the case, and one a fabric could get right with a single live-destination register rather than a counter. The cursor now steps the pair bit fastest: two bursts to one RAM, then two to the other. Combined with `outstandingPerId = 4` (was 2) the crossing request is presented while **two** bursts of that ID are outstanding elsewhere, which is what makes the fabric's per-ID count, and not just its destination compare, part of what is being tested. `Axi4OrderingProbe` confirms the case is reached rather than assumed, and the build fails if it is not.
- **The protocol checker's overflow bit folds into the hardware verdict** (`sysCtrl + 0x10` bit 3, and `io.busViolation`). `Axi4ProtocolChecker` tracks a bounded number of outstanding transactions and says so when it runs out; a run that overflowed has a checker whose silence means "stopped counting", not "saw nothing". That was reported on the serial line and read back over JTAG-AXI, but did not affect pass/fail, so a board could report a clean bus on evidence the checker had already disclaimed. It now fails the run on both boards: it is folded into the `B` the Arty prints, and the DE25-Nano runner, which reads the whole word back over JTAG-AXI, names which of the two it was. The reduction is registered — both halves of the verdict are, since they are read at the end of a run and nowhere else, and each checker's contributing bit is already sticky, so a cycle's delay latches the same result. That is not cosmetic: the unregistered OR across every port took `stress_qos` on the Arty from +0.044 ns to **−0.007 ns** WNS and the build stopped closing at 100 MHz. Registered, it closes at **+0.075 ns** — better than before the bit existed.
- **The `verdict` build runs on the blocking crossbar** (`maxOutstanding = 1`) on both boards. The blocking and pipelined engines are separate RTL paths, and every bitstream in this repository was built on the pipelined one — the blocking engine was covered in simulation only. `verdict` is the quiet build, where a fabric that stalls shows up as a boot that never finishes rather than as a statistic, so it is the one that can carry the other engine without losing what it was measuring. The five stress builds stay pipelined.
- **The Arty report line is 12 bytes** (`VZPDRCLBGS5`), gaining `G` for the traffic generators and `S` for the stream island beside the existing `B`. A check the build leaves out reads upper case, so the line has the same shape whatever the configuration and one parser reads every variant.
- **`run_vexzero_test.py` and `run_vexzero_de25.py` take `--design`**, covering the self test and the five stress builds, with `--design all` running the lot on one board without re-enumerating USB between bitstreams.
- **Timing is a gate on both hardware runners.** `run_vexzero_test.py` and `run_vexzero_de25.py` read the worst slack the build reported and refuse to program or report a board result when it is negative. Both tools write a bitstream whether or not timing closed, and a setup violation shows up as occasional wrong bits rather than a halt, so a run that programs such a bitstream can print a pass that means nothing — which is exactly what happened here: `stress_qos` was certified `VZPDRCLBGSF` / **PASSED** with 821 failing endpoints. `--allow-timing-failure` still programs one, for investigating the path that failed, and says plainly that the result is not evidence. The Vivado flow also records the implementation strategy beside the slack, because an Fmax without the strategy that produced it is not reproducible.
- **The QoS arbiter takes the maximum of the requesters' effective QoS as a balanced tree.** `Seq.reduce` is left-associative, so it built a chain of M−1 comparators where a tree of depth ceil(log2 M) does — four levels rather than three on the DE25-Nano stress builds, which carry five masters, on the path that feeds the grant.
- **The DE25-Nano lights LEDR 4, 5 and 6** on a bus-protocol, generator or stream failure respectively, so a board with the cable unplugged says which part gave up rather than only that something did.

### Deprecated

- **The six MicroBlaze Arty suites are retired** (base, wrr, qos, qos_stress, axi3, axis) as of 2026-09-08. They are no longer run, no longer maintained and no longer a gate on a push. **Nothing has been deleted** — the scripts still work, and each runner now prints a retirement notice; see [`hw/vivado/arty_a7/RETIRED.md`](hw/vivado/arty_a7/RETIRED.md) for the replacement map. Each of those designs pulls in ten or eleven Xilinx IP cores plus a block design, so none could ever be built for Altera, and a hardware suite that runs on one vendor's silicon is evidence about one vendor's silicon. The parts doing the testing were never the Xilinx parts: the traffic generators in `ip/rtl/` are our own portable Verilog, and `axi_sat_gen.v` in particular lives on as `AxiSatGen`. - **QoS exercised at system level, and the condition under which it stops working** — the stress load is re-run under `QosBased` arbitration with the two masters' ranks swapped, at two burst lengths. Swapping the ranking moves **9.2 points of bus share with 4-beat bursts and 0.3 with 16-beat ones**: the crossbar boosts a waiting master's effective priority by one per cycle and saturates it at 15, so a burst long enough to make the loser wait past its own distance from 15 erases the gap before the arbiter sees it, and arbitration falls back to round-robin. That is the anti-starvation mechanism behaving as specified, but it means a QoS gap has to exceed the expected wait in cycles to do anything — which no unit test shows, because it only appears when transactions are long enough to make masters wait. Neither ranking starves the loser in either regime.

- **Decode-error responses (`decode_error_response`, on by default)** — an address that decodes to no slave used to be simply ignored: the crossbar drove AWREADY/ARREADY only for addresses it could place, so the master held its request waiting for a handshake that never came and the port was wedged permanently, with no error and no diagnostic. Both crossbars now carry an internal `Axi4DecErrSlave` that owns every unmapped address, accepts the handshake and completes the transaction with `DECERR` — on B for a write, and on all `len + 1` beats of a read with RLAST on the last — carrying the requesting master's ID so the response routes back through the ordinary path. It is wired in as one more slave in the address decode, so arbitration, W routing and ID-based response routing needed no special case. Cost is one state machine per direction for the whole fabric. - **`VexZeroVideoQosSpec`, and the limit it found** — the obvious way to give a CPU priority over a video core is `QosBased` with `cpuQos = 15`, and it does nothing at all: both policies produce byte-identical counts and latencies at either burst length. AXQOS ranks masters competing for one slave *on one channel*, and the crossbar arbitrates reads and writes independently, with separate grant logic and separate per-slave age state (`wrQosAge` for AW, `rdQosAge` for AR). The CPU's active port issues only reads and the video core only writes, so the two never meet in an arbiter and no AXQOS value can order them; where they do meet is the RAM's single address channel, merged by `toShared()` downstream of the arbiter AXQOS feeds. - **`Axi4ProtocolChecker` — a passive, synthesizable AXI4 protocol checker** (`hw/spinal/axizero/verif/`). 19 rules, one sticky bit each held until reset, exposed as a vector plus a single `any` wire. It is an `Area` rather than a `Component`, so it snoops a bus in place, reads only VALID/READY/payload and drives nothing: adding one cannot change what the design does. Handshake stability on all five channels, W and R beat counts against AxLEN, LAST placement, responses with nothing outstanding, reserved AxBURST, WRAP lengths, 4 KiB crossing, and a configurable burst-length ceiling. Write address and write data are queued independently and judged when both halves arrive, because AXI4 permits data before address; read beats are counted per ID, because AXI4 permits read data for different IDs to interleave and a single counter would fire on legal traffic. Running out of tracking state sets `overflow` rather than raising a rule — it says the checker stopped being able to see everything, not that the bus misbehaved. This exists because the alternatives do not cover the designs under validation: `AxiMonitor` checks four things and is simulation-only, and AMD's 160-rule `axi_protocol_checker` is a block-design IP that cannot go into a plain RTL project, cannot run in SpinalSim, and cannot be built for Altera at all. The same source runs in simulation, on Artix-7 and on Agilex 5. See [ADR 003](docs/adr/003-synthesizable-protocol-checker.md).

- **`AxiProfile`** — per-port traffic shape sampled at the crossbar's master ports: transaction counts, burst-length histograms, peak transactions in flight, end-to-end latency — mean and worst case, since "bounded latency" is a claim about the maximum and a mean stays comfortable while one starved transaction waits arbitrarily long — stall cycles, plus how often more than one master had a request up. Shared by the profile and stress tests so both report the same way.

- **`axi_sat_gen` — a saturating, self-checking AXI4 generator for the QoS stress design.** Every generator this design had ran one transaction at a time, waiting in a B state for each response before presenting the next address, and every one of them tied AR and R off. A master that never has a second request outstanding cannot keep an address channel busy, so the arbiter was rarely asked to choose and an arbitration policy had little to act on; and with no generated reads at all, AR arbitration saw only the CPU and nothing ever checked what came back. This one keeps up to four bursts in flight with AW running ahead of W — the case the crossbar's per-slave W-route FIFO exists for — and reads back every word it writes, comparing each against a value derived from the word's own offset and the pass index. Burst length varies by pass (1, 2, 4, 8 beats), which is what makes an arbitration ranking decay, since a waiting master's priority ages one step per cycle. It replaces `axi_qos_rand_burst_gen` as the third stress master, on the same port list, so no block-design rewiring was needed.

### Fixed

- **A blocking slave took the next write's data as if it were the one it was holding.** Both blocking write engines — the full AXI4 crossbar's and the AXI4-Lite crossbar's own copy — own a slave from the AW that starts a write until the B that ends it, and forwarded the granted master's W channel for that entire window. Nothing in it said which write a beat belonged to. AXI4 lets a master present the next write's data before its address, and there are two ways in: before the AW is accepted, where W is offered alongside the presented address so an IPIF-style slave that wants AWVALID and WVALID together can handshake; and after it, once the burst's last beat has gone through and the response has not come back. In the second case the master cannot have issued its next address anywhere — blocking mode holds a master to one slave at a time — so a beat taken then is certainly the next write's, and it was written under the previous write's address, at a slave that write was never addressed to. Each engine now carries a `wrDataDone` bit per slave, set when the data it was given is complete (WLAST, or every beat for Lite, which has no bursts) and cleared by the response, that shuts W in both windows. The pipelined path was fixed for the pre-AW case earlier in this release and is unaffected; this is the same rule in the two engines that did not get it. `BlockingWriteBoundarySpec` covers all three: both windows on the full crossbar and the response window on the all-Lite one.
- **The YAML front end accepted port widths that cannot be built.** `addr_width` and `data_width` were only checked for being non-negative integers, so `addr_width: 0` described an address channel with no bits and `data_width: 1` or `data_width: 24` a data channel whose WSTRB — one bit per byte lane — cannot match it. `fabric_data_width` had the same hole below one byte. Widths are now whole power-of-two byte lanes of at least 8, which is what `Axi4Config` accepts, and the AXI4-Stream path already required. The six AXI4-Stream signal options are checked for being booleans too: they reach the emitted Scala through `str().lower()`, so `use_last: 1` emitted `useLast = 1`, which does not compile. An unparseable `base` or `size` now reports the same `ERROR:` line as every other bad field instead of a Python traceback.
- **A read overtook an earlier read that carried the same ID.** AXI4 requires transactions sharing an ID and a direction to complete in the order they were issued, whichever slave each went to — the ID is the master's statement of what it is willing to have reordered, and the fabric may not reorder the rest. The pipelined crossbar counted outstanding work per slave and routed responses home by ID, and neither mechanism looks at ordering: two reads carrying one ID, one to a slow slave and one to a fast one, came back in completion order. A CPU that issues a refill and a load under the same ID gets them swapped, which is silent — the data is correct, it arrives against the wrong request. Present since the pipelined mode was written (v0.1.0, 28d84bb), which is why it is filed here and not against a recent change. Fixed with the industry's single-slave-per-ID rule (see `idThreads` above): an ID may have work outstanding at one slave only, and a request naming a second one waits. `ResponseStabilitySpec` now issues two same-ID reads across a slow slave and a fast one and requires issue order; the old fabric returned them 0x50, 0x51 — backwards.
- **A master writing to two slaves at once had its write data taken by both.** W has carried no ID since AXI3, so a master's write beats go in the order of its own AWs and the fabric must steer each burst to the slave its AW went to. The pipelined mode did that with a queue per *slave* naming the master whose data comes next, which is only enough while a master owes data to one slave. With a second AW accepted elsewhere while the first burst's data was still owed, both queues named that master at their heads: both slaves forwarded its W beats, both drove its WREADY, and last-assignment-wins decided which. One beat went to two slaves and the next was stranded — the write never completed and the port wedged. Also present since v0.1.0. Fixed with NIC-400's extended write rule, tracked from the master's own AW and W handshakes: a master may not address a new slave until every write it has already issued has sent its last W beat. Per-ID tracking alone would not have covered it, because a master using two IDs may legally have writes at two slaves. Two tests cover it — a directed one in `ResponseStabilitySpec` that checks each slave holds the word meant for it, and a randomized one in `AxiSatGenSpec` driving a generator whose window straddles the slave boundary under B and R back-pressure. Against the old fabric the directed test stranded the second beat and the randomized one hung at zero laps.

  The ordering table has one case worth naming, because it hid for a while during this work: a slave may answer in the cycle it accepts the address — an AXI4-Lite register file does, which is what `LiteSameCycleResponseSpec` was written for — so a transaction can retire on the cycle it is claimed. Reading the thread's ID register to decide whether a response belongs to it misses that release, because the register does not hold the new ID until the end of the cycle, and a claim that is never given up pins its master to one slave for good: every later read to anywhere else goes unacknowledged. The release now tests the ID the thread holds *this* cycle. It cost a full SoC debug to find, and nothing caught it — the suite reads such a slave in several places, but nothing read one and then read somewhere else. `LiteSameCycleResponseSpec` now does, and fails without the fix.

  Neither bug was reachable from anything this repository puts on a board, which is why ten passing bitstreams never saw them. VexRiscv's load/store port goes through `toAxi4Shared()`, whose command fork does not release the next command until the previous W beat is taken, so the CPU is never owed data at two slaves; the traffic generators and the video writer each stay inside one slave; and every master here drives a constant ID, which the new rule leaves untouched. They are reachable by any master that does not — which is the point of a general-purpose interconnect.

- **A slave that took write data before the address wrapped the fabric's write counters.** AXI4 orders the handshakes on a channel and nothing at all between channels, so a slave may raise WREADY while still holding AWREADY low. The pipelined crossbar offers a master's W beat alongside the AW it is presenting — the bypass that exists so an IPIF-style Lite slave, which will not raise AWREADY until AWVALID and WVALID are both up, can complete its handshake at all — and such a slave therefore takes the beat before the address. The data was never at risk: the bypass only runs while the W route is empty, so the beat goes to the slave the AW is aimed at. The counters were. The W-route FIFO was popped for an entry it never had, and the write-data debt added above was discharged before it was incurred; both wrapped. A wrapped debt names a slave the master is not writing to, and the extended write rule then refuses the address — including one already presented to a slave with AWVALID high, which withdraws a VALID that AXI4 A3.2.1 requires to stay up. The port never recovers. Beats that run ahead of their address are now tracked and excluded from both counters, and an AW whose burst the bypass already delivered in full pushes no route entry and incurs no debt; arbitration bookkeeping follows the AW handshake rather than the push, since the slave owes a B for every address it accepted whatever became of the data. Closing the accounting hole is only half of it: the forwarding path has to close as well once that burst's data is all sent. W runs ahead of AW in the master's own address order, so the beats after it belong to the master's *next* address — still stuck behind the stalled one, and free to name a different slave. Left open, the slave swallows that burst's data: sent to the wrong slave outright if it was addressed elsewhere, or given a route entry and a debt that can never be discharged if it was addressed here. It reopens when the stalled address is finally accepted. Nothing in the suite could produce any of this — every slave model here accepts an address before it offers to take data. `ChannelSkewSpec` now models one that does not: the old fabric hangs its AW forever, and a fabric that fixes only the counters hands the second burst's beats to the wrong slave.
- **A Lite slave answering as the next address arrived returned it under the wrong ID.** `Axi4FullToLiteAdapter` remembers the ID of the transaction in flight and puts it back on the response, because a Lite slave has none, and it took the live ID whenever the address channel was firing — correct for a slave that answers in the cycle it accepts the address, wrong the moment two transactions overlap, because then the response leaving belongs to the *previous* one. It was written under the belief that the crossbar sends a Lite slave one transaction at a time, and only asserted it. The crossbar makes no such promise: the ordering rule added above holds one ID to one slave, and says nothing about two different IDs at the same slave, which is exactly what a multi-ID master produces. The consequence lands on the ordering table — one ID is answered twice and the other never, so its thread is never released and that ID can never reach another slave again. The adapter now holds the address channel closed until the response has gone back, which is what makes taking the live ID sound: an address can only fire with nothing outstanding. `ChannelSkewSpec` drives two IDs at one Lite slave across the handover; the old adapter trips its own assertion.
- **A master with no ID of its own had its responses routed to master 0.** `copyAwToSlave` and `copyArToSlave` encoded the originating master into the slave-side ID only when the master port had `useId` set, so an ID-less master left the field at zero and the return path decoded every one of its responses as master 0's. Only reachable by building `Axi4Crossbar` directly with a multi-master config containing an ID-less port — `AxiZeroMixedTop` rebuilds its internal ports as ID-bearing — but that is supported API. The master index now goes in regardless; only the low bits come from the master.
- **The YAML front end accepted `true` where it wanted a number.** `isinstance(True, int)` is true in Python, so `max_outstanding: true`, `id_threads: true`, a port's `data_width`, `addr_width` or `id_width`, and a weighted-round-robin `weights` entry all passed validation and emitted `= True` or `Seq(True)` into the generated Scala, which does not compile — the error arrived from scalac, pointing at a file the user never wrote. Every integer field now goes through a check that excludes `bool`.
- **The DE25-Nano build reported no timing at all.** `build_vexzero_de25.tcl` located the static-timing report and never read it, so a Quartus run said nothing about whether it closed. It now parses the worst setup slack out of the Setup Summary table and writes it where the Python runner can gate on it. Verified across all five builds on the board: worst setup slack +10.304 to +13.376 ns against a 20 ns period, every design programmed and every verdict word read back correctly over JTAG-AXI. Three things in that report look like the table and are not — the table-of-contents entry, the pass/fail roll-up row, and the Hold, Recovery, Removal and Minimum Pulse Width tables, which share its column layout — so the parser matches the wide single-column banner, confirms the `Clock ; Slack` column header before trusting a row, and reads slack from the second column rather than the first.
- **An address map reaching the top of the address bus could not be built.** Both crossbars decoded a slave hit as `addr >= base && addr < base + size`, which is not always a comparator that exists: a region ending at the top of the bus makes `base + size` equal to `2**addrWidth` and one bit too wide, and a region starting above a master's reach makes `base` itself too wide. SpinalHDL refuses both with `OUT OF RANGE CONSTANT. Operator UInt < UInt`, so the failure was an elaboration error pointing at generated Scala the user never wrote — no netlist, no waveform, nothing to debug. Neither shape is exotic: the first is any map covering the whole address space or the upper half of it, and the second is what a narrow master sees of a slave a wider master on the same crossbar reaches, since every master decodes in its own address width. The map is already required to have power-of-two sizes and size-aligned bases, so membership is an equality on the tag bits above `log2(size)` — which is always legal to build, folds both of those shapes to constants, and is the cheaper decode as well: one narrow equality rather than two full-width carry chains, on a path that feeds the arbiter's grant. Both crossbars now share the one implementation instead of keeping two copies of a line a comment already claimed were the same. A region past the widest master's reach is now refused when the config is built rather than silently becoming a permanent decode error; the check is against the widest master, so a slave above a narrow master but within a wide one stays legal. Four tests in `DecodeErrorSpec` cover it, including a narrow master beside a wide one, which could not elaborate at all before. `scripts/axizero.py` mirrors the reachability check, so a YAML map that no master can address is rejected with a line number's worth of context instead of an elaboration error in generated Scala the user never wrote -- the YAML front end is the one path that takes an arbitrary address map from outside the repo.
- **The crossbar changed a response while B/RVALID was waiting for B/RREADY.** The same rule as above, one channel over, and it survived the fix to the address channels. Each master's B and R muxes picked among the slaves holding a response for it with a bare `OHMasking.first` over the live valid vector, recomputed every cycle. With responses waiting at two slaves and the master stalling, a lower-numbered slave going valid swapped the response out from under a live VALID: BID and BRESP changed mid-handshake. On R it was worse than a payload swap, because releasing per beat let a burst in progress from one slave be preempted by another — two bursts interleaved to one master, which AXI4 permits only across different IDs, and these masters drive a constant ID. Fixed with `lockResp`, which holds the selection until the response is delivered: to B/RREADY for a single beat, and to RREADY && RLAST for a burst, so a burst is never cut in half. It cannot deadlock — the held slave must keep VALID asserted until READY, the master's READY is not conditioned on any other slave, and the others simply wait, which the crossbar was always free to make them do. Nothing in the suite could see this: every simulated master ties BREADY/RREADY high, VexRiscv never stalls a response, and no spec put one master's responses at two slaves at once — the same blind spot that hid the address-channel bug, one channel over. `ResponseStabilitySpec` closes it, and both of its channel tests were confirmed to fail against the old logic with exactly the predicted symptom before the fix went in.
- **The protocol checker reported a 4 KiB crossing on legal unaligned bursts.** AXI4 A3.4.1 measures a burst from the *aligned* start address — only the first transfer may be unaligned — so the last byte is `Aligned + beats*size - 1`. The checker measured from the unaligned address, overstating the span by up to `size-1` bytes: `0xFF2` with four 4-byte beats really spans `0xFF0..0xFFF` and is legal, but appeared to reach `0x1001` and to cross. A false alarm rather than a fabric fault, but it sat in the one component whose whole value is being trusted, and no master in the repository issues an unaligned burst, so nothing had ever exercised the rule off a word boundary.
- **The crossbar changed an address while AxVALID was waiting for AxREADY.** Both crossbars re-evaluated their arbitration grant every cycle from the live request vector, with nothing holding it across a stall. A master that raised its request while an already-granted address was still waiting for AxREADY could win the next cycle, and the address, ID and length presented to the slave changed underneath it — AXI4 A3.2.1 requires them to stay constant from the cycle AxVALID is asserted until AxREADY. AxVALID never dropped and no handshake was lost, both requests were real and both were issued eventually, so every value-based check still passed: 133 simulation tests and six Arty hardware suites had run over it. A slave that latches the address before asserting READY — which is a normal thing to do for timing — latches the wrong one. Found by `Axi4ProtocolChecker` the first time it was pointed at a loaded crossbar, reported as `s0: AR_UNSTABLE`. Fixed with `lockGrant` at all six *address*-channel arbitration sites (blocking and pipelined, read and write, full and Lite): the grant is held from AxVALID to AxREADY. It costs no throughput, because the held master was going to be served in that cycle anyway. The response channels had the same defect and are fixed separately below.
- **Hardware re-validated on both boards after the response-channel fix, the ordering rules and the channel-skew fixes.** Every tracked netlist was regenerated and all ten bitstreams rebuilt from scratch: Arty A7-100T 5/5 PASSED (`verdict` +0.364 ns / 103.8 MHz / 2210 LUTs / 2725 FFs / 3 BRAM, the four stress builds +0.044 to +0.766 ns, 3556-4178 LUTs) and DE25-Nano 5/5 PASSED (worst setup slack +9.640 to +12.504 ns, 6291.4-7989.1 ALMs, verdict words `0x00000106` and `0x00000706`), every build with zero failing endpoints. `stress_qos` is the thin one at +0.044 ns on the Arty, and it is the build whose run-to-run spread the README already documents -- six builds of it now span +0.026 to +0.540 ns on source whose differences add a register or a handful of gates and no combinational depth, and two consecutive rounds of fixes landed it at +0.026 and +0.044, which is placement noise rather than a trend. Vivado 2025.2 on `xc7a100tcsg324-1` at 100 MHz and Quartus Prime Pro 26.1 on `A5EB013BB23BE4SR1` at 50 MHz, default strategies in both, and 157 SpinalSim + 23 vexZero + 36 cocotb + 24 generator tests green against the same source.

- **Four Arty hardware suites could report success without having run.** `run_base_test.py`, `run_wrr_test.py`, `run_qos_test.py` and `run_axi3_test.py` printed their pass banner on `g_fail == 0` alone, never comparing `g_pass` against the number of checks the firmware contains, and the Python only inspected the subprocess exit status, which xsdb sets to 0 whether the test passed, failed or never started. A bus wedged on the first access leaves `g_fail = 0` and `g_pass = 0`, so the suite printed "ALL TESTS PASSED" and exited 0 — the only thing standing between that and a green CI run was a human reading the counter in the log. The banner now requires `g_fail == 0 && g_pass == N` (10, 3, 4 and 5 respectively, each printed alongside the observed value), and a new `run_capture()` reads xsdb's output so the runner exits non-zero on a failure banner, a missing pass banner, or `no targets found`. `run_axis_test.py` and `run_qos_stress_test.py` already did this; the pattern is now uniform.
- **Arty builds failed at random in unrelated Xilinx IP, and the docstring claimed a fix that was not one.** Every out-of-context IP synthesis run loads tclapp from the shared per-user store, and concurrent runs contend over it: an arbitrary subset dies with `ERROR: [Common 17-354] Could not open 'C' for writing` inside `tclapp::load_apps`. `vivado_env()` redirects `APPDATA` to a repo-local directory, which keeps axiZero builds from colliding with other Vivado work on the same machine, and its docstring implied that closed the race. It does not — the runs within a single build still share the redirected store. Measured on Vivado 2025.2 with the redirect in place: `launch_runs synth_1 -jobs 4` failed four builds out of five, `-jobs 1` failed none out of four. Every `create_project*.tcl` now serializes synthesis, which costs wall-clock on a build with many IP but is the thing that actually works; implementation still runs with the requested job count. The docstring says which of the two does what.
- **The base suite reported an AXI protocol checker verdict when no checker was in the bitstream.** `enable_axi_pc` defaults to 0 and `run_base_test.py` passes no `-tclargs`, so the checker is normally absent; the GPIO channel it would be read through does not exist, and the read returns 0 — indistinguishable from "160 rules, no violations". The runner now inspects the block design that produced the bitstream (the only trustworthy source, since it skips the build when a bitstream already exists) and prints `NOT BUILT INTO THIS BITSTREAM` with the flag needed to enable it, rather than a clean-looking `0x0`. The `axi_pc_sticky.v` header also described a 16-chunk-OR view that the RTL has never implemented; it now documents the actual `view[29:0] = sticky_full[59:30]` mapping and says plainly that rules 0..29 and 60..159 reach only the `any_violation` bit.
- **`main_axi3.c` T5 incremented the pass counter without checking anything.** It read the UART status register, discarded the value and called `pass()`, so it would have passed with the read data bus tied off. It now polls `TX_EMPTY` with a bounded loop — so a stuck path fails the test instead of hanging it — and checks `RX_FULL` is clear, since nothing drives the UART receiver on this board.
- **`run_qos_stress_test.py` printed generator probes with expectations that could never hold.** `probe_g2` was labelled `expect 0xB3005502`, but G2's payload is LFSR-randomised per beat over random addresses, so word 0 has no fixed value; two consecutive runs returned `0xB30703E1` and `0xB307039C`. `probe_g0` and `probe_g1` carried values implying pass 0. None of the three was ever compared to anything — they are diagnostics, and the block now says so, with labels describing the encoding instead of a value that never matches.
- **The example SoC corrupted a word of its own boot image during reset, on some simulation seeds.** SpinalHDL's `Axi4SharedOnChipRam` gates its memory write on `stage0.fire && stage0.write` and the W strobes, none of which is qualified by reset. `stage0.valid` comes from the unburstify buffer's valid, which is a *synchronously* reset register — so on the very first clock edge it still holds its power-up value, and a design that comes up with that bit set writes one beat of whatever the address, data and strobe lines happen to carry straight into the RAM. SpinalSim randomises power-up state per seed, which made this look intermittent while being perfectly deterministic for a given seed: on seed 1071835402 the byte `0xCE` landed in `0x80001228` before the CPU fetched its first instruction, and Dhrystone later executed the damaged word, computed a garbage store address and hung. The SoC now masks the RAM's write strobes while reset is asserted, using `isResetActive` — combinational from the reset input, so unlike a guard register it is already correct on that first edge. Reported upstream as [SpinalHDL#1957](https://github.com/SpinalHDL/SpinalHDL/issues/1957) with a standalone reproducer in which 18 of 100 seeds corrupt an initialised RAM with clock and reset as the only stimulus. On an FPGA this is benign at cold start, since registers come up at their INIT value; it bites in simulation that randomises or X-fills initial state, gate-level included, and on a partial or soft reset that leaves a write in flight. A global synchronous warm reset is not affected, because the master's own state resets in the same cycle.
- **`Axi4FullToLiteAdapter` misrouted a response from a Lite slave that answered in the same cycle it accepted the address.** AXI permits a slave to raise RVALID with ARREADY, and small register files commonly do. The adapter returned each response with an ID captured into a register on the address handshake; a register updates at the end of the cycle, so a same-cycle response went out carrying the previous transaction's ID. The pipelined crossbar routes responses to masters by ID, so the answer never reached the master that asked and that master waited forever. The adapter now takes the live ID whenever the address channel is firing in that cycle, on both the read and the write path. Two conditions kept it hidden: it needs the pipelined crossbar (the blocking path routes by remembered grant and never consults the ID) and a slave that answers this fast, where every other Lite slave in the tree holds READY combinationally and answers a cycle later. Found by integrating vtpgZero, not by a testbench.

- **The Arty QoS stress generators read back what they write, and report their own verdict.** `axi_qos_traffic_gen` gained `READ_CHECK`: with it set, each write is followed by a read of the same address whose data is compared in hardware, and the run ends with a status write of `TAG | (resp_errors << 8) | data_errors`. All three stress masters now do this. The firmware waits on those status words instead of on a data sentinel — which distinguishes "the generator never finished" from "it finished and found errors", where a single equality wait folded both into one indistinguishable timeout — and the G2 region check became an exact 128-word comparison. It had been a "at least 32 words were touched and their XOR is non-zero" heuristic, which is all the generator it replaced allowed, since that one wrote random addresses; plain round-robin satisfies such a check as readily as any QoS policy does. `READ_CHECK` defaults off, so the base, WRR and QoS designs are unchanged.
- **`run_qos_stress_test.py` checks the pass counter against the iteration count.** It had judged a 10-minute run on `g_fail == 0`, a live heartbeat and at least one completed iteration, none of which is falsified by sub-tests that silently stop running. Each iteration runs a fixed six sub-tests, on top of one sanity check at startup, so `g_pass` must now land within one iteration's worth of `1 + iterations * 6` — the counter increments at the top of an iteration, so the last one counted is normally still in flight when the monitor samples. The `fail_test` legend and the `probe_g2` label were also stale — the legend never listed the codes the firmware actually used, and `probe_g2` described LFSR-randomised data that the saturating generator no longer produces.
- **`axizero.py example > config.yaml` died on Windows.** The banners and the example YAML carry box-drawing characters, and a redirected stdout defaults to the ANSI codepage, so the command that the help text itself recommends ended in a `UnicodeEncodeError` with a half-written file. Both standard streams are now reconfigured to UTF-8 at startup.
- **The YAML front end accepted two slaves on the same address.** `AxiZeroConfig` rejects overlapping regions, but the generator did not mirror that check, so an overlap in a config file surfaced as a Scala `require` at the far end of an elaboration instead of a line-numbered error. It is now refused up front, along with a non-boolean `reg_slice`, which previously read as true for any non-empty string.
- **`scripts/axizero.py` carried an absolute path.** The sbt search list contained `/tmp/cs_apps/sbt.bat`, a leftover from a development bootstrap that means nothing on another machine.
- **CI ran the generator unit tests before installing PyYAML.** The step passed only because the GitHub runner image happens to ship it; the dependency install now precedes both generator steps.

### Changed

- **`VexZeroSoc` takes an optional third master port** (`hostMaster`), brought out at the SoC boundary rather than instantiated internally, so a simulation can drive it and no vendor primitive has to exist for the SoC to elaborate. The slave-side ID width now follows the master count instead of being fixed at two masters.
- **The self test's verdict moved into `VexZeroChecks`** and the clock/reset generation into `VexZeroBoard`, so the Arty and DE25-Nano wrappers judge and reset identically instead of carrying copies. Rebuilt from these sources, the Arty verdict design is 1091 LUTs at WNS +0.698 ns and still reports `VZPDRCLF` on the board.
- **Dhrystone console parsing moved into `DhrystoneConsole`**, shared by the UART and JTAG paths, so both boards judge a run the same way.
- **`VexZeroSoc` can build its CPU with caches** (`cachedCpu`, `iCacheSize`, `dCacheSize`) — `IBusCachedPlugin` and `DBusCachedPlugin` in place of the simple ones, with `StaticMemoryTranslatorPlugin` marking the 0xF??????? peripheral window as IO so it stays uncached. The address map, the firmware and the prebuilt benchmark binaries are unchanged; what changes is the traffic, from one single-beat transaction per instruction to 8-beat INCR line refills. Dhrystone goes from 0.347 to 0.687 DMIPS/MHz. The two cache sizes are set separately because they answer different questions: the instruction cache decides the score, and the data cache decides whether the load/store port uses the bus at all. Writes are unaffected either way — the data cache has no dirty bit, so it is write-through by construction and no setting makes it burst. The memory-side bus stays 32 bits: a wider one would put the crossbar's width converters under real CPU traffic, but VexRiscv's `DataCache.toAxi4Shared` drives WDATA from a `cpuDataWidth` stage onto a `memDataWidth` bus, so anything else fails to elaborate. The default is still the uncached CPU, so every existing design and every published result is untouched.
- **`VexZeroSoc` gained an optional video path** (`videoBase`, `videoConfig`) — one extra master and one extra Lite slave when set, and nothing at all when not. The master count now drives the slave-side ID width up to four masters.
- **`VexZeroSoc` declares the CPU's AXQOS** (`arbitration`, `cpuQos`) — VexRiscv builds both of its buses with `useQos = false`, so without this the CPU arrives as QoS 0 and can never be ranked above anything. The SoC drives it onto the crossbar's master ports instead. Defaults are round-robin and QoS 0, so existing designs are unchanged.

## [0.3.0] — 2026-03-14

### Added

- **QoS-based arbitration** (`arbitration: qos`) — highest `AXQOS` value wins contention; equal QoS falls back to round-robin. Masters without `useQos` are treated as QoS 0. AXI4-Lite crossbar falls back to pure round-robin (no QoS field).
