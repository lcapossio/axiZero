# Changelog

All notable changes to axiZero will be documented in this file.

## [Unreleased]

### Added

- **VexRiscv example SoC** (`hw/examples/vexriscv/`) — a RISC-V core booting through the crossbar into a mixed AXI4 / AXI4-Lite address map: VexRiscv IBus + DBus as the two masters, an 8 KB on-chip RAM on a full AXI4 port, and AXI4-Lite GPIO and system-control peripherals. Built as a separate sbt project (`vexZero`) against a pinned `third_party/VexRiscv` submodule; the root project neither aggregates nor depends on it, so a checkout without the submodule is unaffected. See [ADR 002](docs/adr/002-vexriscv-example-soc.md).
- **`vexzero.Rv32`** — a small RV32I encoder that assembles the example's boot firmware at elaboration time, so the SoC test needs no RISC-V cross compiler and no binary is tracked in git. Verified byte-identical to `riscv64-unknown-elf-as` for the whole program.
- **`VexZeroSocSpec`** — 3 tests: boot to completion on the pipelined crossbar, on the blocking crossbar, and a check that the assembled firmware image matches the documented program.
- **`VexZeroArty`** — an Arty A7-100T board wrapper for the example SoC. It reruns the SoC's checks in hardware and reports the verdict on LD4–LD7 and as a repeating 9-byte line on the USB-UART (115200 8N1), the last byte being the switch nibble the firmware read back over AXI4-Lite. Verified on the board: `VZPDRCLF`, 1091 LUTs, 1142 registers, 3 block RAM tiles, WNS +0.698 ns at 100 MHz (107.5 MHz Fmax) with Vivado 2025.2 on `xc7a100tcsg324-1`.
- **`VexZeroArtySpec`** — simulates the board wrapper and decodes its report line from `uart_rxd_out` at the real 115200 8N1, so a broken report is caught in a two-minute run instead of a twenty-minute Vivado round trip.
- **`run_vexzero_test.py`** — hardware test runner for the example SoC: generates the netlist, builds the bitstream, programs the Arty over JTAG and checks the serial verdict. Needs only Vivado and xsdb; there is no MicroBlaze in the design, so no `mb-gcc`.
- **CI job `VexRiscv example SoC`** — initialises only the VexRiscv submodule, then runs scalafmt, the boot tests, and the netlist generator.
- **Dhrystone benchmark on the example SoC** — `VexZeroBenchArty` runs the prebuilt RV32I `dhrystoneO3.hex` that ships with the pinned VexRiscv submodule and streams the benchmark's own console over the USB-UART. On the Arty A7-100T at 100 MHz: 328,048 cycles for 200 runs (1640.2 per run), 60,967 Dhrystones/s, **0.347 DMIPS/MHz**, all 20 self-checks passing — cycle-for-cycle identical to simulation. Blocking mode (`max_outstanding = 1`) costs 1.2% (331,848 cycles, 0.343 DMIPS/MHz). Measured at the crossbar's master ports: instruction fetch 153,191 reads at 3.04 cycles average AR→R latency; load/store 17,953 reads at 3.00 cycles and 18,796 writes at 3.09 cycles AW→B — the three-cycle floor of the registered path, so the fabric never queued under this load. Resources for the whole benchmark SoC: 1213 LUTs, 1263 registers, 9 block RAM tiles, 0 DSPs, WNS +0.521 ns (105.5 MHz Fmax), Vivado 2025.2 on `xc7a100tcsg324-1`.
- **`VexZeroBenchIo`** — a third AXI4-Lite slave implementing the console MMIO of VexRiscv's own regression testbench (`0xF00F_F000`: putchar, cycle counter, exit, error), so upstream firmware images run unmodified. Its putchar register backpressures: a full UART FIFO stalls the CPU's store rather than dropping a character.
- **`HexImage`** — an Intel HEX reader (records 00/01/04/05, checksums verified) that loads a prebuilt firmware image into the SoC's RAM at elaboration time, so a benchmark needs no cross compiler and no binary enters git.
- **`VexZeroBenchSpec`** — 3 tests: Dhrystone on the pipelined crossbar and on the blocking crossbar, both re-running the benchmark's own self-checks and asserting per-port AXI latency, plus a board-level test that decodes the whole console off `uart_rxd_out`.
- **`VexZeroBoard`** — the clock and reset generation both Arty wrappers share, so they cannot drift apart.
- **`run_vexzero_bench.py`** — hardware runner for the benchmark: opens the serial port before programming (the program runs once at configuration), streams the console, then re-runs Dhrystone's self-checks and recomputes the score from the cycle count.
- **DE25-Nano (Altera Agilex 5) support for the example SoC** — `VexZeroDe25` and `VexZeroBenchDe25` run the same SoC, crossbar and firmware on a Terasic DE25-Nano, built with Quartus Prime Pro. The interconnect needed no change and no vendor-specific primitive: the port is ordinary inferred RTL plus a different way of reporting. Verified on the board: the self test passes with every checked value read back over JTAG-AXI, and Dhrystone runs to completion with its console drained through the bridge, all 20 self-checks passing and exit code 0 — in **328,048 cycles for 200 runs, the same count as the Arty and as simulation**, so the design does identical work on Agilex 5 and Artix-7. 4,589 ALMs / 6,618 registers / 6 RAM blocks (self test) and 4,802 / 6,861 / 19 (benchmark), 0 DSPs, worst-case slack +12.824 ns and +12.631 ns with zero failing endpoints, reported Fmax 139.35 MHz and 135.70 MHz. Quartus Prime Pro 26.1 on `A5EB013BB23BE4SR1` at 50 MHz. Those figures include the JTAG bridge, which has no counterpart in the Arty builds.
- **JTAG-to-AXI bridge as a third bus master** (`JtagAxi`) — the DE25-Nano has no UART, so instead of the design pushing a report out, the host reaches in: fpgacapZero's bridge joins the crossbar as M2 and the runner reads the registers the firmware wrote. This puts the report path inside the system under test — every checked value is arbitrated against a CPU that is still fetching. The bridge is wrapped as a plain axiZero master port, with the vendor TAP primitive chosen by a parameter (Intel today, Xilinx 7-series named).
- **`fcapz` submodule bumped to v0.4.9** — the existing fpgacapZero submodule now also carries the JTAG-to-AXI bridge RTL and the host-side Python library the DE25-Nano runner drives it with, so the two cannot drift apart. Every module the existing Arty debug flows instantiate has an unchanged port list across the bump.
- **Host-drainable benchmark console** — `VexZeroBenchIo` gained an optional buffer the host reads out over the bus (`0x000` pops a character, `0x004` the level, `0x008` done), plus readback of the exit code, for boards with no serial port. Backpressure is unchanged: a full buffer stalls the store rather than dropping a character.
- **`VexZeroHostSpec`** — 3 tests covering the three-master arrangement without the vendor primitive: the host reading the verdict across both Lite and full-AXI4 slaves, dozens of host reads interleaved with instruction fetch (all correct, firmware result unchanged), and a whole Dhrystone run drained through the console buffer with its own self-checks re-run on the text.
- **`run_vexzero_de25.py`** — hardware runner for the DE25-Nano: generates the netlist, builds with Quartus, programs over the USB-Blaster, then reads the verdict or drains the benchmark console through the JTAG-AXI bridge.
- **`VexZeroStressSpec` — a system-level stress test, because Dhrystone alone is not one** — the same SoC with caches on and a third master saturating the fabric at the same RAM slave the CPU is fetching from: 16-beat INCR bursts, several outstanding, AW deliberately ahead of W. The fabric goes from 7.9% occupied and 0.0% contended to **99.9% occupied and 60.4% contended**, instruction-fetch latency rises from 10.0 to 23.8 cycles and data-read latency to 34.0, and **971,146 burst beats are checked against their expected values with zero mismatches** while Dhrystone still passes all 20 of its own self-checks and exits zero. Run over both crossbar modes: at this occupancy the two are level (85,153 transactions in 1,033,503 cycles pipelined against 82,548 in 999,762 blocking, 0.2% apart per cycle) but split the bandwidth differently — the pipelined path completes 4.5% more host bursts and costs Dhrystone 4.3%. The load is bandwidth-bound at one slave; the pipelined path's advantage is concurrency across different slaves, which `PipelinedArbitrationSpec` measures directly.
- **`VexZeroProfileSpec` — what a benchmark run actually asks of the interconnect**, measured at the master ports rather than asserted, across three CPU configurations. Uncached Dhrystone is 189,937 transactions of which every one is a single beat, never more than two in flight, with the two masters colliding in 1.1% of cycles: maximum possible coverage, close to minimum possible pressure. This is why the 1.2% pipelined-vs-blocking figure measures fabric overhead and not throughput. The other two columns pin down the load/store port specifically: a 4 KiB data cache holds Dhrystone's whole working set and misses 63 times in a run, while a 512 B one issues 3,327 line refills — and **no configuration produces a single write burst**, because VexRiscv's data cache has no dirty bit and is write-through by construction.
- **vtpgZero as a pinned submodule, joining the example SoC as a fourth master** (`third_party/vtpgZero`, Apache-2.0) — a synthesizable video test pattern generator whose AXI4-Stream output is turned into AXI4 write bursts by the core's own stream-to-memory writer. It arrives as two ports at once: a write-only master filling a framebuffer in RAM, and the AXI4-Lite slave that programs it, on the same crossbar, so configuring the generator is arbitrated traffic too. This is the **first bursting write master in the design that is real hardware** — VexRiscv's data cache has no dirty bit and cannot produce one, and the stress test's bursts come from a simulation-only Scala generator. It is also the first blackbox here that simulates: both modules are plain Verilog-2001 with no vendor primitives, so Verilator compiles the submodule's own sources. `VexZeroSoc` gained `videoBase` and `videoConfig`; both default off, so every existing design is unchanged. Initialise it non-recursively — it carries its own `fcapz` submodule pointing at the fpgacapZero this repository already pins.
- **`VexZeroVideoSpec`** — 2 tests. The wrapper's control port on its own, which separates a fault in the core from one in the fabric in seconds; and the whole path, where a 32×32 frame becomes **64 write bursts of 16 beats, 1,024 beats, and zero read commands**, with all 1,024 pixels read back and checked exactly. The pattern is solid colour so every pixel word is predictable and a burst written to the wrong address fails rather than merely looking wrong.
- **`LiteSameCycleResponseSpec`** — pins the adapter fix below with an AXI4-Lite slave that raises ARREADY and RVALID together, modelled on the one that found it. Reverting the fix makes its first read hang.
- **QoS exercised at system level, and the condition under which it stops working** — the stress load is re-run under `QosBased` arbitration with the two masters' ranks swapped, at two burst lengths. Swapping the ranking moves **9.2 points of bus share with 4-beat bursts and 0.3 with 16-beat ones**: the crossbar boosts a waiting master's effective priority by one per cycle and saturates it at 15, so a burst long enough to make the loser wait past its own distance from 15 erases the gap before the arbiter sees it, and arbitration falls back to round-robin. That is the anti-starvation mechanism behaving as specified, but it means a QoS gap has to exceed the expected wait in cycles to do anything — which no unit test shows, because it only appears when transactions are long enough to make masters wait. Neither ranking starves the loser in either regime.
- **`HostTraffic`** — a checking AXI4 traffic generator for the SoC's third master port. Five cooperating sim threads, one per channel group, so AR keeps issuing while R is still draining and AW runs ahead of W — the case per-slave W routing exists for. Burst length and AXQOS are parameters, so the same generator supplies both the saturating load and the QoS experiment. Every read carries the value it expects, so a mis-routed or dropped beat fails the test rather than merely slowing it.
- **Decode-error responses (`decode_error_response`, on by default)** — an address that decodes to no slave used to be simply ignored: the crossbar drove AWREADY/ARREADY only for addresses it could place, so the master held its request waiting for a handshake that never came and the port was wedged permanently, with no error and no diagnostic. Both crossbars now carry an internal `Axi4DecErrSlave` that owns every unmapped address, accepts the handshake and completes the transaction with `DECERR` — on B for a write, and on all `len + 1` beats of a read with RLAST on the last — carrying the requesting master's ID so the response routes back through the ordinary path. It is wired in as one more slave in the address decode, so arbitration, W routing and ID-based response routing needed no special case. Cost is one state machine per direction for the whole fabric. Set the key to `false` to restore the old behaviour.
- **`DecodeErrorSpec`** — 13 tests: unmapped reads and writes on the blocking crossbar, on the pipelined crossbar and on the Lite crossbar; an unmapped 8-beat burst read answered with exactly 8 DECERR beats and one RLAST; an unmapped write burst whose W beats are all sunk before the response, checked by the mapped write that follows; a decode error returned to master 1 while master 0's mapped read completes, which is where a lost master index would show; decode errors under `QosBased`, under `WeightedRoundRobin` and under blocking-plus-QoS, plus two masters erroring on both engines at once, because the responder resizes the per-slave credit and QoS-age state and an off-by-one there would corrupt a real slave's arbitration rather than its own; two masters contending *at the responder* with different AXQOS, raced in both orderings for reads and for writes, which is the only case that reaches the responder's own entry in those QoS-age arrays — a decode error racing a mapped access leaves each slave with a single requester and never compares two priorities; and one test that pins the unacknowledged failure mode itself, with the responder disabled, so what it prevents stays visible.
- **The Scala API is documented (`Quick start`, Option C)** — the three tops (`AxiZeroLiteTop`, `AxiZeroFullTop`, `AxiZeroMixedTop`), the `AxiZeroConfig` that parameterises all of them, and the `io.masters` / `io.slaves` convention, with a worked example that was compiled and run before being written down rather than typed out plausibly. This was the more capable of the two front ends and the only undocumented one: the YAML generator emits Scala that calls exactly this API, so anything YAML can express Scala can, plus configurations the schema does not reach.
- **Publication metadata (`description`, `homepage`, `licenses`, `scmInfo`, `developers`)** — every publish target requires these and Maven Central rejects a POM without them. Setting them commits to no destination and needs no credentials, so `sbt publishLocal` and any future release agree on what the artifact says about itself. `publishLocal` produces `io.axizero:axizero_2.13:0.1.0` with jar, sources and Scaladoc; axiZero is still published nowhere public, so consuming it externally means a source dependency or a local publish.
- **`VexZeroVideoQosSpec`, and the limit it found** — the obvious way to give a CPU priority over a video core is `QosBased` with `cpuQos = 15`, and it does nothing at all: both policies produce byte-identical counts and latencies at either burst length. AXQOS ranks masters competing for one slave *on one channel*, and the crossbar arbitrates reads and writes independently, with separate grant logic and separate per-slave age state (`wrQosAge` for AW, `rdQosAge` for AR). The CPU's active port issues only reads and the video core only writes, so the two never meet in an arbiter and no AXQOS value can order them; where they do meet is the RAM's single address channel, merged by `toShared()` downstream of the arbiter AXQOS feeds. The test also records that there is nothing to arbitrate at this memory: single-cycle on-chip RAM, about 63% asked for between the two masters, every video burst served in exactly its own transfer time and a two-cycle worst-case instruction fetch. It asserts the equality between policies so that the day a shared port gains QoS-aware merging, the claim fails rather than quietly going stale.
- **`AxiProfile`** — per-port traffic shape sampled at the crossbar's master ports: transaction counts, burst-length histograms, peak transactions in flight, end-to-end latency — mean and worst case, since "bounded latency" is a claim about the maximum and a mean stays comfortable while one starved transaction waits arbitrarily long — stall cycles, plus how often more than one master had a request up. Shared by the profile and stress tests so both report the same way.

- **`axi_sat_gen` — a saturating, self-checking AXI4 generator for the QoS stress design.** Every generator this design had ran one transaction at a time, waiting in a B state for each response before presenting the next address, and every one of them tied AR and R off. A master that never has a second request outstanding cannot keep an address channel busy, so the arbiter was rarely asked to choose and an arbitration policy had little to act on; and with no generated reads at all, AR arbitration saw only the CPU and nothing ever checked what came back. This one keeps up to four bursts in flight with AW running ahead of W — the case the crossbar's per-slave W-route FIFO exists for — and reads back every word it writes, comparing each against a value derived from the word's own offset and the pass index. Burst length varies by pass (1, 2, 4, 8 beats), which is what makes an arbitration ranking decay, since a waiting master's priority ages one step per cycle. It replaces `axi_qos_rand_burst_gen` as the third stress master, on the same port list, so no block-design rewiring was needed.

### Fixed

- **Four Arty hardware suites could report success without having run.** `run_base_test.py`, `run_wrr_test.py`, `run_qos_test.py` and `run_axi3_test.py` printed their pass banner on `g_fail == 0` alone, never comparing `g_pass` against the number of checks the firmware contains, and the Python only inspected the subprocess exit status, which xsdb sets to 0 whether the test passed, failed or never started. A bus wedged on the first access leaves `g_fail = 0` and `g_pass = 0`, so the suite printed "ALL TESTS PASSED" and exited 0 — the only thing standing between that and a green CI run was a human reading the counter in the log. The banner now requires `g_fail == 0 && g_pass == N` (10, 3, 4 and 5 respectively, each printed alongside the observed value), and a new `run_capture()` reads xsdb's output so the runner exits non-zero on a failure banner, a missing pass banner, or `no targets found`. `run_axis_test.py` and `run_qos_stress_test.py` already did this; the pattern is now uniform.
- **Arty builds failed at random in unrelated Xilinx IP, and the docstring claimed a fix that was not one.** Every out-of-context IP synthesis run loads tclapp from the shared per-user store, and concurrent runs contend over it: an arbitrary subset dies with `ERROR: [Common 17-354] Could not open 'C' for writing` inside `tclapp::load_apps`. `vivado_env()` redirects `APPDATA` to a repo-local directory, which keeps axiZero builds from colliding with other Vivado work on the same machine, and its docstring implied that closed the race. It does not — the runs within a single build still share the redirected store. Measured on Vivado 2025.2 with the redirect in place: `launch_runs synth_1 -jobs 4` failed four builds out of five, `-jobs 1` failed none out of four. Every `create_project*.tcl` now serializes synthesis, which costs wall-clock on a build with many IP but is the thing that actually works; implementation still runs with the requested job count. The docstring says which of the two does what.
- **The base suite reported an AXI protocol checker verdict when no checker was in the bitstream.** `enable_axi_pc` defaults to 0 and `run_base_test.py` passes no `-tclargs`, so the checker is normally absent; the GPIO channel it would be read through does not exist, and the read returns 0 — indistinguishable from "160 rules, no violations". The runner now inspects the block design that produced the bitstream (the only trustworthy source, since it skips the build when a bitstream already exists) and prints `NOT BUILT INTO THIS BITSTREAM` with the flag needed to enable it, rather than a clean-looking `0x0`. The `axi_pc_sticky.v` header also described a 16-chunk-OR view that the RTL has never implemented; it now documents the actual `view[29:0] = sticky_full[59:30]` mapping and says plainly that rules 0..29 and 60..159 reach only the `any_violation` bit.
- **`main_axi3.c` T5 incremented the pass counter without checking anything.** It read the UART status register, discarded the value and called `pass()`, so it would have passed with the read data bus tied off. It now polls `TX_EMPTY` with a bounded loop — so a stuck path fails the test instead of hanging it — and checks `RX_FULL` is clear, since nothing drives the UART receiver on this board.
- **`run_qos_stress_test.py` printed generator probes with expectations that could never hold.** `probe_g2` was labelled `expect 0xB3005502`, but G2's payload is LFSR-randomised per beat over random addresses, so word 0 has no fixed value; two consecutive runs returned `0xB30703E1` and `0xB307039C`. `probe_g0` and `probe_g1` carried values implying pass 0. None of the three was ever compared to anything — they are diagnostics, and the block now says so, with labels describing the encoding instead of a value that never matches.
- **The example SoC corrupted a word of its own boot image during reset, on some simulation seeds.** SpinalHDL's `Axi4SharedOnChipRam` gates its memory write on `stage0.fire && stage0.write` and the W strobes, none of which is qualified by reset. `stage0.valid` comes from the unburstify buffer's valid, which is a *synchronously* reset register — so on the very first clock edge it still holds its power-up value, and a design that comes up with that bit set writes one beat of whatever the address, data and strobe lines happen to carry straight into the RAM. SpinalSim randomises power-up state per seed, which made this look intermittent while being perfectly deterministic for a given seed: on seed 1071835402 the byte `0xCE` landed in `0x80001228` before the CPU fetched its first instruction, and Dhrystone later executed the damaged word, computed a garbage store address and hung. The SoC now masks the RAM's write strobes while reset is asserted, using `isResetActive` — combinational from the reset input, so unlike a guard register it is already correct on that first edge. Reported upstream as [SpinalHDL#1957](https://github.com/SpinalHDL/SpinalHDL/issues/1957) with a standalone reproducer in which 18 of 100 seeds corrupt an initialised RAM with clock and reset as the only stimulus. On an FPGA this is benign at cold start, since registers come up at their INIT value; it bites in simulation that randomises or X-fills initial state, gate-level included, and on a partial or soft reset that leaves a write in flight. A global synchronous warm reset is not affected, because the master's own state resets in the same cycle.
- **`Axi4FullToLiteAdapter` misrouted a response from a Lite slave that answered in the same cycle it accepted the address.** AXI permits a slave to raise RVALID with ARREADY, and small register files commonly do. The adapter returned each response with an ID captured into a register on the address handshake; a register updates at the end of the cycle, so a same-cycle response went out carrying the previous transaction's ID. The pipelined crossbar routes responses to masters by ID, so the answer never reached the master that asked and that master waited forever. The adapter now takes the live ID whenever the address channel is firing in that cycle, on both the read and the write path. Two conditions kept it hidden: it needs the pipelined crossbar (the blocking path routes by remembered grant and never consults the ID) and a slave that answers this fast, where every other Lite slave in the tree holds READY combinationally and answers a cycle later. Found by integrating vtpgZero, not by a testbench.

- **The Arty QoS stress generators read back what they write, and report their own verdict.** `axi_qos_traffic_gen` gained `READ_CHECK`: with it set, each write is followed by a read of the same address whose data is compared in hardware, and the run ends with a status write of `TAG | (resp_errors << 8) | data_errors`. All three stress masters now do this. The firmware waits on those status words instead of on a data sentinel — which distinguishes "the generator never finished" from "it finished and found errors", where a single equality wait folded both into one indistinguishable timeout — and the G2 region check became an exact 128-word comparison. It had been a "at least 32 words were touched and their XOR is non-zero" heuristic, which is all the generator it replaced allowed, since that one wrote random addresses; plain round-robin satisfies such a check as readily as any QoS policy does. `READ_CHECK` defaults off, so the base, WRR and QoS designs are unchanged.
- **`run_qos_stress_test.py` checks the pass counter against the iteration count.** It had judged a 10-minute run on `g_fail == 0`, a live heartbeat and at least one completed iteration, none of which is falsified by sub-tests that silently stop running. Each iteration runs a fixed six sub-tests, on top of one sanity check at startup, so `g_pass` must now land within one iteration's worth of `1 + iterations * 6` — the counter increments at the top of an iteration, so the last one counted is normally still in flight when the monitor samples. The `fail_test` legend and the `probe_g2` label were also stale — the legend never listed the codes the firmware actually used, and `probe_g2` described LFSR-randomised data that the saturating generator no longer produces.

### Changed

- **`VexZeroSoc` takes an optional third master port** (`hostMaster`), brought out at the SoC boundary rather than instantiated internally, so a simulation can drive it and no vendor primitive has to exist for the SoC to elaborate. The slave-side ID width now follows the master count instead of being fixed at two masters.
- **The self test's verdict moved into `VexZeroChecks`** and the clock/reset generation into `VexZeroBoard`, so the Arty and DE25-Nano wrappers judge and reset identically instead of carrying copies. Rebuilt from these sources, the Arty verdict design is 1091 LUTs at WNS +0.698 ns and still reports `VZPDRCLF` on the board.
- **Dhrystone console parsing moved into `DhrystoneConsole`**, shared by the UART and JTAG paths, so both boards judge a run the same way.
- **`VexZeroSoc` can build its CPU with caches** (`cachedCpu`, `iCacheSize`, `dCacheSize`) — `IBusCachedPlugin` and `DBusCachedPlugin` in place of the simple ones, with `StaticMemoryTranslatorPlugin` marking the 0xF??????? peripheral window as IO so it stays uncached. The address map, the firmware and the prebuilt benchmark binaries are unchanged; what changes is the traffic, from one single-beat transaction per instruction to 8-beat INCR line refills. Dhrystone goes from 0.347 to 0.687 DMIPS/MHz. The two cache sizes are set separately because they answer different questions: the instruction cache decides the score, and the data cache decides whether the load/store port uses the bus at all. Writes are unaffected either way — the data cache has no dirty bit, so it is write-through by construction and no setting makes it burst. The memory-side bus stays 32 bits: a wider one would put the crossbar's width converters under real CPU traffic, but VexRiscv's `DataCache.toAxi4Shared` drives WDATA from a `cpuDataWidth` stage onto a `memDataWidth` bus, so anything else fails to elaborate. The default is still the uncached CPU, so every existing design and every published result is untouched.
- **`VexZeroSoc` gained an optional video path** (`videoBase`, `videoConfig`) — one extra master and one extra Lite slave when set, and nothing at all when not. The master count now drives the slave-side ID width up to four masters.
- **`VexZeroSoc` declares the CPU's AXQOS** (`arbitration`, `cpuQos`) — VexRiscv builds both of its buses with `useQos = false`, so without this the CPU arrives as QoS 0 and can never be ranked above anything. The SoC drives it onto the crossbar's master ports instead. Defaults are round-robin and QoS 0, so existing designs are unchanged.

## [0.3.1] — 2026-03-15

### Fixed

- **`Axi4DownsizerExt` FIXED burst multi-beat crash** — FIXED bursts with `len > 0` caused simulation deadlocks because the downsizer emitted multi-beat sub-AW transactions with incorrect data interleaving. Sub-transactions for FIXED bursts are now flattened to single-beat (`len=0, burst=INCR`), with addresses cycling through byte lanes within the wide word.
- **`Axi4DownsizerExt` WRAP burst wrap-around failure** — WRAP bursts that crossed the wrap boundary within a sub-AW transaction produced incorrect addresses because the downstream slave computed its own (narrower) wrap boundary. Sub-transactions for WRAP bursts are now flattened to single-beat (`len=0, burst=INCR`), with the sub-transaction generator computing all wrapped addresses internally.

### Added

- **`BurstTypeSpec`** — 6 tests: INCR 2-beat baseline, FIXED 1-beat and 2-beat overwrite, WRAP 2-beat aligned, WRAP 4-beat aligned, WRAP 4-beat with actual wrap-around.
- **`ArbitrationSpec`** — 7 tests: FixedPriority (smoke, contention, 3-master ordering) and WeightedRoundRobin (smoke, weight proportionality, equal-weight fairness, data integrity).
- **`RegSliceAndLiteWidthSpec`** — 8 tests: Full AXI4 register slices (master/slave/both, multi-beat burst), Lite register slices (master/both), AXI4-Lite width conversion (16→32 upsizing, multiple addresses).
- **`PipelinedArbitrationSpec`** — 9 tests: pipelined FixedPriority (smoke, contention, concurrent bursts), pipelined WRR (smoke, weight-3 wins, data integrity), pipelined QoS (write contention, read contention, data integrity).
- **`NarrowPortSpec`** — 6 tests: narrow slave 32→16 (single-beat, burst, scattered), narrow master 16→32, mixed concurrent Full+Lite from 2 masters.

### Changed

- SpinalSim test count: 40 → 76 (36 new tests across 5 new suites), 13 suites total.
- INCR burst path in `Axi4DownsizerExt` is unchanged (multi-beat sub-AW for efficiency).

## [0.3.0] — 2026-03-14

### Added

- **QoS-based arbitration** (`arbitration: qos`) — highest `AXQOS` value wins contention; equal QoS falls back to round-robin. Masters without `useQos` are treated as QoS 0. AXI4-Lite crossbar falls back to pure round-robin (no QoS field).
- **Aging-based anti-starvation** — per-master age counters increment each cycle a request is pending but not granted (saturates at 15). Effective QoS = min(rawQoS + age, 15), so a starved QoS-0 master eventually matches QoS 15 and gets served.
- **`QosCrossbarSpec`** — 5 SpinalSim tests: higher AWQOS wins (blocking and pipelined), higher ARQOS wins, equal-QoS round-robin tie-break, aging prevents starvation of low-QoS requester.
- **QoS hardware test** — 2-master stress harness (MicroBlaze + traffic generator) on Arty A7-100T with `ArtyQosDutGen`, `rename_qos_ports.py`, and `run_qos_test.py`. All 4 HW tests pass (g\_fail=0, g\_pass=4).
- **cocotb QoS test suite** — 6 cocotbext-axi integration tests (`sim/cocotb_gen/qos/test_qos.py`): dual-master R/W, address routing, higher QoS wins contention, equal-QoS round-robin, aging anti-starvation, QoS read priority.
- **QoS example design** — `MyFull_2M2S_QoS` added to `scripts/example.yaml` (2-master, 2-slave, full AXI4, QoS arbitration, `max_outstanding=4`).
